# Roadmap / План работ

Актуальный план развития форка **proxydroid** (ветка по умолчанию — `main`).
Файл — единственный источник истины по тому, что делаем дальше и в каком порядке.

## Как мы работаем (release flow)

```
1. Одна фича = одна ветка feat/* от main
2. Открываем PR в main
3. Хотим проверить APK на устройстве ДО мержа:
   ставим на PR метку 'publish-rc'
   → prerelease-from-pr.yml собирает APK
   → публикует в rolling pre-release v<version>-rc (APK перезаписывается)
4. Скачиваем APK из Releases, ставим, проверяем
5. Всё ок → мержим PR в main
6. auto-tag-release.yml видит изменение version.properties
   → ставит тег v<version>
7. release-apk.yml собирает и публикует полноценный релиз
```

Версия живёт в `version.properties` (единственное место). Правила:

| Что меняем | Как бампать | Пример |
|---|---|---|
| Новая фича | `VERSION_MINOR + 1`, `PATCH = 0` | 3.5.0 → 3.6.0 |
| Багфикс | `VERSION_PATCH + 1` | 3.5.0 → 3.5.1 |
| Ломающее изменение | `VERSION_MAJOR + 1`, остальные в 0 | 3.5.0 → 4.0.0 |

`versionCode` вычисляется как `MAJOR*10000 + MINOR*100 + PATCH`.

## План: следующие фичи (в порядке приоритета)

### 1. Индикатор живости соединения 🟢 простая

**Зачем:** показать в UI, что прокси реально работает, а не просто «включён».

**Куда:**
- `app/src/main/java/org/proxydroid/utils/NetworkUtils.kt` — метод проверки живости (например, короткий TCP-connect к `host:port` или лёгкий HTTP-запрос через прокси с timeout).
- `app/src/main/java/org/proxydroid/ui/MainViewModel.kt` — состояние `isAlive: Boolean` в `MainUiState`, метод проверки.
- `app/src/main/java/org/proxydroid/ui/MainScreen.kt` — индикатор в `ConnectionCard` (например, маленькая точка/иконка рядом со статусом).

**Критерий готовности:** при включённом VPN индикатор зелёный, при потере — красный.

---

### 2. Периодический опрос живости по таймеру 🟡 средняя

**Зачем:** держать индикатор актуальным без ручного действия пользователя.

**Куда:**
- `MainViewModel.kt` — `viewModelScope` + `delay` loop (например, раз в 10–30 секунд), обновляет `isAlive`.
- Учитывать жизненный цикл: запускать опрос при `isWorking == true`, останавливать при выключении.

**Критерий готовности:** индикатор обновляется сам при потере/восстановлении соединения.

---

### 3. Автопоиск прокси в локальной сети на порту 10808 🔴 сложная

**Зачем:** автоматически находить прокси в LAN (например, другой телефон, раздающий прокси), вместо ручного ввода IP.

**Куда:**
- `NetworkUtils.kt` — новый метод поиска (скан подсети, корутины, timeout, порт по умолчанию **10808**).
- `MainViewModel.kt` — запуск поиска, состояние «идёт поиск / найден адрес».
- `MainScreen.kt` — кнопка «Найти прокси в сети» + отображение результата.

**Критерий готовности:** в сети с прокси на 10808 — находится за несколько секунд; в сети без прокси — корректно сообщает «не найдено».

---

### 4. Повтор поиска прокси при потере соединения 🟡 средняя

**Зачем:** если соединение потеряно (или прокси пропал), автоматически повторить поиск и переподключиться.

**Зависит от:** #1 (индикатор) + #2 (таймер) + #3 (автопоиск).

**Куда:**
- `MainViewModel.kt` — по результату периодического опроса при потере соединения запускать автопоиск (#3) и повторное подключение.

**Критерий готовности:** при выключении/смене прокси приложение само находит новый и восстанавливает соединение.

---

### 5. Автозапуск с дефолтными настройками после перезагрузки

**Статус:** базовый механизм уже сделан в PR #2 (опция **Start on boot**).

**Что осталось:** убедиться, что после перезагрузки применяется именно дефолтный/текущий профиль без ручного вмешательства; если нужно — доработать логику выбора профиля при старте.

## Известные техдолги

- Релизные workflow читают версию из `version.properties` — при добавлении нового компонента версии обновлять парсер во всех workflow'ах.
- `emulator-test` в `android-build.yml` помечен `continue-on-error: true` (не валит сборку, т.к. нестабилен на хостед-раннерах). Вернуть в блокирующие, когда стабилизируется.
- **Автобамп `version.properties` при мерже PR** (см. отдельный раздел ниже) — сейчас bump ручной, легко забыть → релиз не создастся.

## Доработка: автобамп версии при мерже PR

**Проблема.** Сейчас bump `version.properties` — **ручная операция в PR-ветке перед мержем**. Если забыть:

- `auto-tag-release.yml` **не сработает** (его триггер — `push` в main с `paths: ['version.properties']`, а файл не менялся);
- новый тег не появится → `release-apk.yml` не запустится → **релиза не будет**;
- в истории остаётся «фича смержена, а версия не двинулась».

Уже дважды всплывало: PR #4 (индикатор живости) требовал ручного `VERSION_MINOR=5 → 6`.

**Цель.** При мерже PR автоматически инкрементить нужный компонент версии так, чтобы `auto-tag-release` гарантированно срабатывал.

### Варианты решения

**Вариант A — метка на PR (рекомендуемый).**

Workflow `bump-on-merge.yml`, триггер `pull_request: types: [closed]` + условие `merged == true`:

| Метка на PR | Действие | Пример |
|---|---|---|
| `bump:minor` | `MINOR + 1`, `PATCH = 0` | 3.6.0 → 3.7.0 |
| `bump:patch` | `PATCH + 1` | 3.6.0 → 3.6.1 |
| `bump:major` | `MAJOR + 1`, `MINOR = 0`, `PATCH = 0` | 3.6.0 → 4.0.0 |
| (нет метки) | ничего — для docs/chore PR | — |

Плюсы: осознанный сигнал (как `publish-rc`), не нужно угадывать тип, легко проверить глазами.
Минусы: лишний шаг при мерже (ставим метку).

**Вариант B — автоопределение по содержимому.** Workflow смотрит на изменённые файлы в PR: фичи в `app/src/main/**` → MINOR, только багфиксы → PATCH. Плюс: без ручных действий. Минус: эвристика легко ошибается.

**Вариант C — PR-комментарий-команда.** Бот слушает `/bump minor` или `/bump patch` в PR. Плюс: гибко. Минус: сложнее, нужно помнить синтаксис.

**Рекомендация:** **Вариант A** (метка) — совпадает с моделью меток в проекте (`publish-rc`), минимально сложен, не ошибается.

### Что нужно сделать (при реализации Варианта A)

1. Добавить в репо метки `bump:minor`, `bump:patch`, `bump:major`.
2. Создать `.github/workflows/bump-on-merge.yml`:
   - триггер `pull_request: [closed]`, `if: github.event.pull_request.merged`;
   - по метке вычислить новую версию и обновить `version.properties` в `main`;
   - закоммитить с `[skip ci]` (чтобы не зациклить);
   - `auto-tag-release.yml` подхватит → тег → `release-apk.yml` → релиз.
3. Обновить `ROADMAP.md` / `docs/SESSION-*.md`, описав процесс.
4. Оставить ручной bump как fallback.

### Открытые вопросы

- Нужен ли `bump:major` в реальности, или мажор всегда бампаем руками?
- Конфликт: PR уже сам бампнул `version.properties`, а метка просит бампнуть ещё раз? Решение: если файл изменён в PR — не дублировать.
