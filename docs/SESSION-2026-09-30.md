## Release flow (как работает)

```
1. Одна фича = одна ветка feat/* от main
2. Открываем PR в main
3. Проверка APK ДО мержа: ставим метку 'publish-rc' на PR
   → prerelease-from-pr.yml собирает APK
   → публикует в rolling pre-release vX.Y.Z-rc (APK перезаписывается через --clobber)
4. Скачиваем APK из Releases, ставим, проверяем
5. Всё ок → мержим PR в main
6. auto-tag-release.yml видит изменение version.properties → ставит тег vX.Y.Z
7. release-apk.yml собирает и публикует полноценный релиз
```

**ВАЖНО:**
- **«Релиз, связанный с PR» ДО мержа — это только `vX.Y.Z-rc` (pre-release)**. Полноценный релиз появляется **только после мержа**.
- `gh release upload --clobber` **перезаписывает APK-ассет**, но **НЕ меняет `published_at`** релиза. Поэтому в `list_releases` timestamp остаётся старым — это НЕ значит, что APK старый. Реальное время заливки видно в логах шага `Publish rolling pre-release`.

## Версионирование

`version.properties` — единственное место версии.

| Что меняем | Как бампать | Пример |
|---|---|---|
| Новая фича | `VERSION_MINOR + 1`, `PATCH = 0` | 3.5.0 → 3.6.0 |
| Багфикс | `VERSION_PATCH + 1` | 3.5.0 → 3.5.1 |
| Ломающее | `VERSION_MAJOR + 1` | 3.5.0 → 4.0.0 |

`versionCode = MAJOR*10000 + MINOR*100 + PATCH`.

## Рабочие правила (от пользователя)

### Правило #1: сам ставлю метку `publish-rc`
Когда сборка PR зелёная — я **сам** ставлю метку `publish-rc` через `add_labels`, ДО того как предлагать скачать APK. Порядок:
1. Сборка PR зелёная → 2. ставлю метку → 3. проверяю фактом (`get_pull_request`, `list_workflow_runs`) → 4. жду завершения RC → 5. проверяю фактом что APK залит (`get_run_logs_by_step`) → 6. только тогда сообщаю: «APK готов, скачивай»

### Правило #2: верифицирую результат инструмента
НЕ делать вывод «сработало» по ответу `✅ ok`. ВСЕГДА проверять фактом:
- `create_or_update_file` → `get_file_contents`
- `create_branch` → `get_branch`
- `add_labels` → `get_pull_request`
- `dispatch_workflow` → `list_workflow_runs`
- CI-фикс → `get_workflow_run_status`
- релиз → `get_run_logs_by_step` / `list_releases`

**Латентность GitHub:** между `add_labels` и run'ом — 1–3 минуты. Подождать и перепроверить, не делать вывод по первому снимку.

### Правило #3: summary сессии
Я **не вижу** метрики контекста (токены, %). Счётчик в UI (напр. 927K) — накопленное за сессию, НЕ окно запроса. Окно DeepSeek V3/V3.1/R1 = 64K, V3.2-Exp = 128K. Риск обрыва оценивать по симптомам. Делать summary: по команде, в естественных точках (крупная задача), при симптомах обрыва.
